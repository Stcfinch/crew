# ADR-006：為何文件用錨點指向程式碼，而非抄寫程式碼內容

- 日期：2026-07-28（feature-workflow@5.0.0 + bug-workflow@4.0.0 同期）
- 狀態：已採用

## 背景

使用者實際用 CREW 開發功能後回報三個問題：

1. **Token 太貴** —— 開發一個功能要寫一大堆文件
2. **中斷即遺忘** —— 流程跑到一半斷掉，`plan-close` 沒做到
3. **文件不可信** —— 中途改了程式但文件沒同步，久了大家還是只看程式碼

盤點後確認這**不是三個獨立問題，是同一個根因的三種症狀**：

> `.spec/` 文件大量抄寫了「程式碼才是唯一事實」的內容（code-truth）——
> 欄位清單、方法簽章、類別清單、DDL、檔案清單。

實測證據（2026-07-28，使用者本機 13 個真實 `.spec/` 目錄）：

| 項目 | 數字 |
|------|------|
| 一個 feature 的產出檔數 | 12–17 檔 |
| 完整案例純文字 | 1893–2385 行 |
| `spec.md` | 平均 425 行（n=38，max 1107） |
| `arch.md` | 平均 535 行（n=27，max 1865） |
| 同一份 DDL 出現次數 | 3–4 次（`db.md`／`db.sql`／`deploy.sql`／`deploy-checklist.md`） |
| 反向漂移檢查（文件落後程式碼） | **0 個** |

抄寫同時造成三件事：抄寫本身是篇幅大宗（Token）、抄本在程式碼一改就過期且沒有
任何檢查抓得到（漂移）、文件越多越難在中斷後接續（遺忘）。

候選方案：

- **A**：加強同步紀律 —— 要求 `plan-build` 產碼後回頭更新 `spec.md`／`db.md`／`arch.md`
- **B**：加自動同步 —— 寫工具從程式碼反向生成文件段落
- **C**：**讓文件不再承載 code-truth**，「是什麼」一律用錨點指向程式碼

## 決策

採方案 **C**。

`plan.md` 只寫**程式碼裡看不到的東西**：需求、決策與理由、被否決的方案與否決理由、
驗收條件、已知取捨。「是什麼」用可機器驗證的錨點指過去：

```markdown
- 鎖定計數改走 Redis（原因：多節點 in-memory 會漏算）
  → `@code:src/.../LoginAttemptService.java#recordFailure` (L88)
- 表結構見 `@sql:deploy.sql#login_attempt`
```

正規形 `@code:<相對路徑>[#<符號>]` 與 `@sql:deploy.sql#<表名>`。
行號 `(L88)` 刻意放在 token **外面** —— 它是給人看的提示，script 只回報新行號、不判失敗。

符號比對用 **word-boundary 字串比對，不做 AST** —— 要能跨 Java/XML/SQL/YAML，
且 AST 才是誤判主因。

新的漂移形式（**指標本身會失效**）由三層承接：

| 層 | 機制 | 是否阻擋 |
|----|------|---------|
| 偵測 | `check-spec-drift.py`（D1–D7，exit 0/1/2/3） | — |
| 修復 | `/plan-drift`：機械型自動修，語意型逐條確認 | 否 |
| 把關 | `plan-close` 硬關卡，在 `git add -f` 與 Notion 同步**之前** | FAIL 擋、WARN 明示放行 |

## 後果

**正面**

- `.spec/` 純文字 1893–2385 行 → **186 行**（減 90–92%）
- `/plan-next` 餵給模型從「讀多檔案＋LLM 讀 18 列決策表推理」→ **85 bytes** 結構化答案
- 文件天然不易過期：決策與理由不會因為改一行程式而失效
- 漂移**首次可被機器偵測**（此前為 0）

**負面**

- 讀文件的人要跳到程式碼才看得到「是什麼」，離線閱讀體驗變差
- 錨點會因改名／刪除而失效 —— 換了一種漂移，不是消滅漂移
- `plan-close` 多一道可能擋住結案的關卡（誤殺風險由「只有 D1/D2 可 FAIL」壓低）
- 破壞性變更：舊 `.spec/` 任務需相容層與遷移路徑（ADR 內含過渡期成本）

**中性**

- `state.json` 111 行看似不小，但它是機器讀的，不進 LLM context

## 考慮過的替代方案

| 方案 | 為何沒選 |
|------|---------|
| **A. 加強同步紀律**（產碼後回頭更新文件） | 這正是已經失敗的做法。`plan-build` 原本就有 E5/E6 兩項 code-vs-doc 抽查，但分級為 WARN 不阻擋，實務上沒人回頭修。要求 LLM「記得同步」與要求人「記得寫註解」是同一類願望，不是機制 |
| **B. 從程式碼反向生成文件** | 生成得出來的東西（欄位、簽章、DDL）本來就在程式碼裡，讀原始碼更準；生成不出來的東西（為什麼這樣設計、否決了什麼）才是文件的價值。這方案會產出「更精美的抄本」，Token 更貴、價值不變 |
| **C-變體：錨點含行號當判定依據** | 行號改幾行就位移，誤報率極高。誤報會導致大家把檢查關掉——這是這類工具最常見的死法。故行號只給人看，不參與判定 |
| **C-變體：錨點用 AST 解析** | 需為每種語言寫 parser，且 CREW 要跨 Java/XML/SQL/JSP/YAML。AST 解析失敗會產生誤報，違反「寧可漏報不可誤報」原則 |
| **遷移時用 LLM 把舊文件摘要進 plan.md** | 425 行壓成 80 行不可驗證，且壓縮就是取捨——LLM 取捨時會補上看似合理、當初根本沒討論過的理由，這些假決策會被後人當成史實。改為機械搬移進 `archive/` ＋ `TODO(migrate)` 佔位由人補 |
