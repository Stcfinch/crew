# plan-explore — 不同進入情境的處理範例

> 供 `plan-explore/SKILL.md` 引用。四段完整範例對話，示範探索模式在不同情境下的姿態與視覺化手法。

**使用者帶來模糊想法：**

```
使用者：我在想要不要做推播標籤查詢的優先順序機制

你：推播優先順序是個有趣的空間。讓我想想...

      推播分類光譜
      ════════════════════════════════════════════

      時效性               重要性              個人化
          │                  │                  │
          ▼                  ▼                  ▼
      ┌────────┐        ┌────────┐         ┌────────┐
      │ 即時   │        │ 關鍵   │         │ 偏好   │
      │ 警報   │        │ 通知   │         │ 標籤   │
      │ 推播   │        │ 推播   │         │ 推播   │
      └────────┘        └────────┘         └────────┘
          │                  │                  │
        不可延遲           可排隊             可批次

      你腦中的「優先順序」比較偏向哪個軸？
```

**使用者想比較選項：**

```
使用者：RabbitMQ 還是直接 HTTP 回呼？

你：得看上下文。推播場景的特性是？

使用者：推播標籤查詢每小時觸發一次，但可能同時觸發 5 萬人

你：那就不一樣了。

     ┌─────────────────────────────────────────────┐
     │         推播觸發資料流                        │
     └─────────────────────────────────────────────┘

     關鍵限制：
     • 5 萬人同時推播
     • 第三方推播通道有速率限制
     • 失敗需要重試

                  RabbitMQ        HTTP 直呼
     背壓控制      有 ✓             無 ✗
     重試機制      內建 ✓           需自建 ✗
     監控          管理介面 ✓       需自建 ✗
     複雜度        需維護 MQ ✗      簡單 ✓

     RabbitMQ。5 萬人的場景下沒有選擇。

     除非... 你們有考慮分批推播？
```
